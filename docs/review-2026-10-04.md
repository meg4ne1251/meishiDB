# 2026-10-04 セキュリティ・機能レビューと修正

API、Web、OCR、scanner-watcherとデプロイ設定を確認した。
前回修正後の既存テストはAPI 182件、Web 34件、OCR 70件、scanner-watcher 19件が成功し、
追加検証では既存テストの対象外だった不具合を再現した。変更はワークスペースに適用済み。

## 指摘と対応

| 優先度 | 問題と影響 | 修正・検証 |
|---|---|---|
| P1 | 更新APIで送信元を検証していない。CORSだけでは単純なPOSTの実行を拒否できず、同一サイトの別オリジンからCookie付きログアウト等を送信できる。 | `browser_security.py`でOrigin/Refererを設定済みURLと完全一致で照合。null、類似ドメイン、不正Referer、送信元不明のcross-site/same-site要求を拒否。実セッションの維持と正常な送信元の操作をテスト。 |
| P2 | 認証の試行制限がなく、パスキーチャレンジも上限なくメモリに蓄積する。 | 接続元・認証エンドポイントごとに20回/60秒、429とRetry-Afterを追加。偽のX-Forwarded-Forで回避できないことと時間経過後の解除を検証。チャレンジは4,096件まで。 |
| P2 | パスキーAPIが自由なdictを受け付け、不正email/credential/base64で未処理例外になる。登録用チャレンジをログイン側でも受け付ける。 | Pydanticで外側の型と長さを検証し、credential IDのbase64エラーを400へ変換。用途違いのチャレンジを拒否。重複登録を400へ変換し、署名カウンタ更新を行ロックで直列化。 |
| P2 | 同じメールの同時登録で、待機前の重複判定を両方が通過しDBの一意制約エラーになる。 | アドバイザリロック取得後に重複を判定。同時POSTが201と400になり、ユーザーが1件だけ残ることを実DBで検証。 |
| P1 | OCR中に別リクエストで入力した氏名を、OCR前に読み込んだ空の値に基づいて上書きする。確定済みステータスも戻してしまう。 | OCR結果の適用前に最新の名刺とフィールドをロックして再読込。PATCHも同じ名刺行で直列化し、現在空の項目だけ補完。処理中に手入力した値とconfirmedを保持し、空の会社欄だけ補完することを検証。 |
| P2 | Meilisearchから最初の200件だけを取得し、201件目以降を一覧・エクスポート対象から落とす。 | 200件ずつ取得。既定上限1,000件ではSQLへフォールバック。205件の検索とページ送りを検証。SQLにもraw_ocr_textを追加。 |
| P2 | サムネイル取得失敗後に原本も取得できないと未処理例外になる。通常の画像404にはストレージの内部エラー文字列が露出する。 | 両経路を同じ汎用404へ変換。原本とサムネイルの欠落時に内部情報を返さないことを検証。 |
| P2 | vCardでCRだけの改行が残り、連絡先テキストの構造を壊し得る。最後の行にもCRLFがない。 | CR/CRLF/LFを正規化してエスケープし、末尾CRLFを追加。3種類の改行をテスト。実連絡先アプリのインポートは未検証。 |
| P2 | お気に入りの同時追加で一意制約エラー、同時共有で重複した共有行ができ得る。 | お気に入りはON CONFLICT DO NOTHING、共有追加/解除は名刺行をロック。並行リクエストでも1行だけ作られることを実DBで検証。既に存在する重複共有データの整理は実施していない。 |
| P2 | 閲覧専用の共有でもフォームが編集可能。共有先には名刺画像が表示されず、所有者の保存・画像処理・共有解除失敗も表示されない。 | APIのcan_editに合わせて編集を制御。共有画像の閲覧を追加し、所有者の撮影・OCR操作は所有者だけに表示。失敗を画面に表示し、入力を保持。React DOMでview/editと保存失敗を検証。APIの既存権限チェックも保持。 |
| P2 | スキャンの画像送信失敗後、再試行のたびに空の名刺を新規作成する。 | 作成済みIDを保持して再試行に利用。処理中の二重送信・画像選び直しを抑止。作成1回・アップロード2回をテスト。 |
| P2 | 画像を差し替えても同じimg URLのため、表示中の画像が更新されない。 | updated_atを画像URLに含めて再取得。更新後にsrcが変わることを検証。 |
| P3 | タグのcolorをnullで消去できない。 | PATCHの省略と明示nullを区別し、色の消去をテスト。 |
| P3 | Webのlint設定がなく、npm run lintが対話画面で終了する。 | Next.js標準の.eslintrc.jsonを追加し、警告・エラーなしで終了することを確認。 |

補強としてAPIの通常応答にprivate, no-storeを付与し、ログインのパスワード長を登録と同じ200文字に制限した。
画像選択はAPIで対応するJPEG/PNG/WebP・15 MiBに合わせ、プレビューのObject URLを解放する。

送信元検証の根拠は[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。
vCardの形式は[RFC 2426](https://www.rfc-editor.org/rfc/rfc2426)、
検索上限は[Meilisearch settings](https://www.meilisearch.com/docs/reference/api/settings/list-all-settings)に照合した。

## 適用条件・検証範囲

`CORS_ORIGINS`には実際にブラウザで開くURLを設定する。VPN名/IPで利用する場合も必要。
本番ComposeではPUBLIC_HOSTからHTTPS URLを設定する。API・Webを再起動/再ビルドして反映する。
今回DBマイグレーションは不要。既存のユーザー作成済み仕様・共有権限・保存データを移行していない。

認証制限は既存の単一APIプロセス構成を前提とする。プロキシ配下でAPIがプロキシのIPを見る場合は
利用者全員で制限を共有する。複数ワーカーではストア共有が必要。公開登録・初回登録者がadminの仕様と
パスキーのuser verification=PREFERREDは維持しており、公開前の初期登録・利用者範囲の管理が必要。
同じ項目の通常編集にはバージョンによる厳密な競合検出はない。複数画像アップロードの順序保証も対象外。

Meilisearchの1,000件到達時はSQLの部分一致へ切り替わり、タイプミス補正は適用されない。
実PaddleOCR推論、MinIO/Meilisearch/Nominatimとの結合、全サービスのDocker起動、
実ブラウザE2E・侵入/負荷試験、全依存の自動脆弱性監査は未実施。
外部サービスはスタブで検証し、DBは実PostgreSQLとAlembicを使用した。

Next.jsはpackage.json/lock/ビルドで15.5.27を確認。
[公式2026年9月更新](https://nextjs.org/blog/september-2026-security-release)の15.5系列の修正バージョンと一致する。
Python依存にはロックがないため、今回テストした環境と再ビルド時の環境の一致までは保証していない。
